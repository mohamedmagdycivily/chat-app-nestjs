A high-performance, scalable chat system built with NestJS. The system provides RESTful APIs for managing applications, chats, and messages with asynchronous processing, race condition handling, and optimized database operations.

## Overview

This chat system allows creating applications where each application has a unique token (generated by the system) and a name (provided by the client). Devices use the token to send chats to that application. The system supports:

- **Applications**: Each application has a unique token and name
- **Chats**: Numbered chats within each application (starting from 1)
- **Messages**: Numbered messages within each chat (starting from 1)
- **Async Processing**: Chat and message creation uses asynchronous processing via RabbitMQ
- **Race Condition Handling**: Atomic operations using Redis and database transactions
- **Count Synchronization**: Periodic sync of chat and message counts (within 1 hour)

## Features

### Core Features

✅ **Application Management**

- Create applications with auto-generated unique tokens
- Update application names
- Retrieve applications by token
- List all applications

✅ **Chat Management**

- Create chats asynchronously (returns 202 Accepted)
- Numbered chats per application (starting from 1)
- Retrieve chats by application token
- Get specific chat by token and chat number

✅ **Message Management**

- Create messages asynchronously (returns 202 Accepted)
- Numbered messages per chat (starting from 1)
- Retrieve messages by chat
- Get specific message by token, chat number, and message number

✅ **Asynchronous Processing**

- Outbox pattern for reliable event publishing
- RabbitMQ for message queuing
- Maxwell CDC for outbox event transformation
- Idempotent event processing

✅ **Race Condition Handling**

- Redis-based atomic number generation
- Database transactions for consistency
- Inbox pattern for idempotent event processing
- Atomic Lua scripts for counter updates

✅ **Count Synchronization**

- `chats_count` column in applications table
- `messages_count` column in chats table
- Cron jobs sync counts from Redis to MySQL every 30 minutes
- Counts are never more than 1 hour behind

✅ **Database Optimization**

- Appropriate indices on foreign keys and unique constraints
- Optimized queries for common operations

### Data Flow

#### Chat/Message Creation Flow

1. **Client Request** → API receives POST request
2. **Validation** → Verify application/chat exists
3. **Number Generation** → Get next number from Redis (atomic INCR)
4. **Outbox Write** → Write event to outbox table (single DB write)
5. **202 Response** → Return immediately with generated number
6. **CDC Processing** → Maxwell detects outbox insert
7. **Event Publishing** → Maxwell publishes to RabbitMQ
8. **Event Handling** → Event handlers process asynchronously:
   - Write to main tables (idempotent)
   - Update Redis counters (atomic Lua scripts)
9. **Count Sync** → Cron jobs sync Redis counts to MySQL

### Key Design Patterns

- **Outbox Pattern**: Ensures reliable event publishing
- **Inbox Pattern**: Ensures idempotent event processing
- **CDC (Change Data Capture)**: Maxwell monitors outbox table
- **Event Sourcing**: Events drive state changes

## Installation & Setup

### 1. Clone the Repository

```bash
git clone <repository-url>
cd chat-app-nestjs
```

### 2. Environment Configuration

Create a `.env` file in the root directory with the following variables:

```env
# Application
NODE_ENV=development
PORT=3001
MODULE_NAME=chat-service

# MySQL Database
MAIN_DB_HOST=main-db
MAIN_DB_PORT=3306
MAIN_DB_DATABASE=chat_db
MAIN_DB_USERNAME=chat_user
MAIN_DB_ROLE=chat_user
MAIN_DB_PASSWORD=chat_password

# Redis
REDIS_HOST=redis-db
REDIS_PORT=6379
REDIS_PASSWORD=redis_password

# RabbitMQ
RABBITMQ_HOST=rabbitmq
RABBITMQ_PORT=5672
RABBITMQ_USER=rabbitmq_user
RABBITMQ_PASS=rabbitmq_password

# Exchanges
CHAT_EXCHANGE=x.chat-service
MESSAGE_EXCHANGE=x.message-service
```

### 3. Build and Run with Docker Compose

The easiest way to run the entire stack:

```bash
docker compose up --build
```

This command will:

- Build the application Docker image
- Start MySQL database
- Start Redis
- Start RabbitMQ with management UI
- Start Maxwell for CDC
- Start the NestJS application
- Run database migrations automatically

### 4. Access Services

Once all services are up:

- **API Server**: http://localhost:3001
- **Swagger Documentation**: http://localhost:3001/api
- **RabbitMQ Management**: http://localhost:15672 (username: `rabbitmq_user`, password: `rabbitmq_password`)

### 5. Verify Setup

Check that all services are healthy:

```bash
# Check running containers
docker compose ps

# Check application logs
docker compose logs chat

# Check database connection
docker compose exec main-db mysql -u chat_user -pchat_password chat_db -e "SHOW TABLES;"
```

## Database Schema

### Tables

#### `apps`

- `id` (BIGINT, Primary Key) - Internal ID (not exposed to clients)
- `token` (BIGINT, Unique) - Application token (exposed to clients)
- `name` (VARCHAR) - Application name
- `chat_count` (INTEGER) - Number of chats (synced from Redis)
- `created_at` (TIMESTAMP)
- `updated_at` (TIMESTAMP)

**Indices:**

- Primary key on `id`
- Unique index on `token`

#### `chats`

- `id` (BIGINT, Primary Key) - Internal ID (not exposed to clients)
- `chat_number` (BIGINT) - Chat number within application (exposed to clients)
- `app_id` (BIGINT, Foreign Key) - Reference to `apps.id`
- `message_count` (BIGINT) - Number of messages (synced from Redis)
- `created_at` (TIMESTAMP)
- `updated_at` (TIMESTAMP)

**Indices:**

- Primary key on `id`
- Index on `app_id`
- Unique composite index on `(app_id, chat_number)`

#### `messages`

- `id` (BIGINT, Primary Key) - Internal ID (not exposed to clients)
- `message_number` (BIGINT) - Message number within chat (exposed to clients)
- `chat_id` (BIGINT, Foreign Key) - Reference to `chats.id`
- `content` (TEXT) - Message content
- `created_at` (TIMESTAMP)
- `updated_at` (TIMESTAMP)

**Indices:**

- Primary key on `id`
- Index on `chat_id`

#### `outbox`

- `id` (BIGINT, Primary Key)
- `event_id` (VARCHAR, Unique) - Event identifier
- `event_type` (VARCHAR) - Event type
- `aggregate_id` (VARCHAR) - Aggregate identifier
- `timestamp` (TIMESTAMP)
- `routing_key` (VARCHAR)
- `exchange` (VARCHAR)
- `data` (JSON) - Event payload
- `created_at` (TIMESTAMP)

#### `inbox`

- `id` (BIGINT, Primary Key)
- `event_id` (VARCHAR, Unique) - Event identifier
- `event_count` (INTEGER) - Number of times event was processed
- `created_at` (TIMESTAMP)
- `updated_at` (TIMESTAMP)

## System Design

### Race Condition Handling

#### Number Generation

- **Redis INCR**: Atomic increment operations for generating unique numbers
- **Key Pattern**: `app:{app_id}:chat_number_generator` and `chat:{chat_id}:message_number_generator`

#### Counter Updates

- **Atomic Lua Scripts**: Ensure counter updates are atomic and idempotent
- **Lock Mechanism**: Prevents duplicate processing of the same event

#### Database Writes

- **Transactions**: All database writes use transactions
- **Unique Constraints**: Database-level constraints prevent duplicates
- **Idempotent Processing**: Inbox pattern ensures events are processed only once

### Asynchronous Processing

#### Outbox Pattern

1. API writes event to `outbox` table (single DB write)
2. Returns 202 Accepted immediately
3. Maxwell CDC detects new outbox record
4. Maxwell publishes to RabbitMQ
5. Event handlers process asynchronously

#### Event Processing

- **Idempotent**: Events can be processed multiple times safely
- **Reliable**: RabbitMQ ensures message delivery
- **Scalable**: Multiple workers can process events concurrently

### Count Synchronization

#### Strategy

- Counts are maintained in Redis for fast updates
- Cron jobs sync Redis counts to MySQL every 30 minutes
- Counts are never more than 1 hour behind (runs every 30 minutes)

#### Implementation

- **Cron Jobs**: Scheduled tasks using `@nestjs/schedule`
- **Sync Frequency**: Every 30 minutes
- **Atomic Updates**: Batch updates with transactions
